# Dynamic Color Theme Customization Solutions

Dynamic theming typically relies on CSS custom properties (variables) to enable runtime color changes. Many existing solutions use JavaScript to adjust CSS variables or swap style sheets, often integrating with frameworks like Tailwind CSS, React, Vue, and Angular. Below is an overview of key approaches and tools, including their capabilities, framework integration, accessibility features, brand control options, and limitations.

## Framework-Agnostic CSS Variable Theming

**CSS Custom Properties and JavaScript:** The most common approach is to define theme colors as CSS custom properties (e.g. `--primary-color`) and update them via JavaScript at runtime. This method is framework-agnostic – any environment that can include CSS and run JS can use it. For example, the **dynamic-theme-switcher** library demonstrates this pattern: it lets you initialize a set of CSS variables and switch to a new set on the fly ([GitHub - timr76/dynamic-theme-switcher: A lightweight library for dynamically switching themes using CSS variables.](https://github.com/timr76/dynamic-theme-switcher#:~:text=About)). Under the hood, this simply applies new values to CSS variables (often on the `:root` or a container element), instantly updating styled elements without a full page reload.

- **Usage:** Typically, a theme is represented as a JavaScript object (keyed by variable names or semantic names). Applying a theme means iterating over these keys and calling something like `document.documentElement.style.setProperty('--variable', value)`. Libraries abstract this; for instance, *dynamic-theme-switcher* provides `ThemeSwitcher.init(defaultTheme)` and `ThemeSwitcher.switchTheme(newTheme)` to swap theme objects ([GitHub - timr76/dynamic-theme-switcher: A lightweight library for dynamically switching themes using CSS variables.](https://github.com/timr76/dynamic-theme-switcher#:~:text=import%20ThemeSwitcher%20from%20%27dynamic)) ([GitHub - timr76/dynamic-theme-switcher: A lightweight library for dynamically switching themes using CSS variables.](https://github.com/timr76/dynamic-theme-switcher#:~:text=import%20ThemeSwitcher%20from%20%27dynamic)).

- **Integration:** Because this approach manipulates global CSS, it works with any framework. You might simply call the theming function in a React effect, an Angular service, or vanilla JS. The styling changes reflect immediately in the UI without needing to re-render components. Kent C. Dodds (EpicReact) even advocates for CSS variables over React Context for theming due to simplicity and performance – CSS variables can be read directly in CSS (`var(--variable)`) without constant JS re-rendering ([Use CSS Variables instead of React Context | Epic React by Kent C. Dodds](https://www.epicreact.dev/css-variables#:~:text=Let%27s%20look%20at%20a%20simple,really%20don%27t%20need%20to%20do)).

- **Example Tools:** Aside from custom scripts, small utilities exist. **theme-change** (by the DaisyUI author) is a lightweight script that toggles CSS themes via data-attributes and persists the choice in localStorage ([daisyUI themes — Tailwind CSS Components ( version 4 update is here )](https://daisyui.com/docs/themes/#:~:text=%3Chtml%20data)). It’s essentially framework-neutral: you attach it to toggles or selects in the DOM, and it switches the active theme’s CSS variables accordingly. Many devs also write their own mini togglers using localStorage and a `<html data-theme="...">` attribute or class.

- **Limitations:** The framework-agnostic approach assumes you’ve predefined which CSS variables exist. You must ensure all UI elements use these variables in their styles. Also, updating variables directly won’t notify JS logic of color changes (if any logic depends on theme values). In practice, this isn’t a major issue since CSS handles it, but it’s a consideration if your components need to know the current theme in code (e.g., to load different icons). Another limitation is **FOUC (flash of unthemed content)** on initial load if theme preference is stored in JS – you might see the default theme briefly before JS applies the new theme. Mitigation involves inlining a quick style or using server-rendered theme attributes.

## Tailwind CSS and Theme Switching

Tailwind CSS by itself is a utility-first, *compile-time* framework – it doesn’t support arbitrary runtime style values because all classes are generated at build time ([How to use Dynamic Variables with Tailwind - DEV Community](https://dev.to/alanscodelog/how-to-use-dynamic-variables-with-tailwind-4309#:~:text=)). However, there are solutions to make Tailwind-based sites themeable:

- **Preset Themes via DaisyUI:** DaisyUI is a popular Tailwind plugin that provides a collection of pre-defined themes using CSS variables. Each theme is a set of color variables (e.g. `--dp-primary`, `--dp-secondary`, etc.), and DaisyUI applies them when you set a `data-theme` attribute on an element (often the `<html>`). Developers list the theme names in `tailwind.config.js`, and DaisyUI generates the corresponding CSS ([daisyUI themes — Tailwind CSS Components ( version 4 update is here )](https://daisyui.com/docs/themes/#:~:text=daisyUI%20comes%20with%20a%20number,theme%20attribute%20to%20HTML%20tag)). For example, you might configure `themes: ["light", "dark", "corporate"]` and then write `<html data-theme="dark">…</html>` to apply the dark theme. Switching themes at runtime is as simple as changing that attribute (DaisyUI’s docs even suggest using the `theme-change` script for toggling and storing the choice) ([daisyUI themes — Tailwind CSS Components ( version 4 update is here )](https://daisyui.com/docs/themes/#:~:text=%3Chtml%20data)).

  - **Integration:** Because DaisyUI operates at the CSS level, it works wherever Tailwind works (React, Vue, etc.). The actual theme toggle can be handled with any JS – e.g., a React onClick that sets `document.documentElement.dataset.theme = "corporate"`. The Tailwind classes remain the same; only the underlying CSS variables change, updating colors on the fly.

  - **Brand Control:** DaisyUI’s themes are pre-set. You can customize or add themes in the config (e.g., define your own color values for a “mytheme”) ([tailwind css - How to customize a theme in daisy-ui? - Stack Overflow](https://stackoverflow.com/questions/70713667/how-to-customize-a-theme-in-daisy-ui#:~:text=%7B%20mytheme%3A%20%7B%20primary%3A%20%22,)). This gives brands control over the palette—developers can enforce brand guidelines by only including approved themes. However, DaisyUI is not designed for end-users to arbitrarily pick colors at runtime; all possible themes must be defined at build time. If a brand wanted to let users customize colors freely, DaisyUI alone wouldn’t suffice without generating new CSS.

  - **Limitations:** The need to predefine themes means truly “dynamic” user-generated themes aren’t straightforward. If, say, user A wants a blue accent and user B wants green, you’d have to generate those theme definitions in advance or inject new styles dynamically (which falls back to manual CSS variable manipulation). Also, DaisyUI’s set of theme variables is fixed (primary, secondary, accent, etc.), so if you need additional custom properties, you must extend it carefully. Another limitation is that DaisyUI is Tailwind-specific; it ties into Tailwind’s build process and wouldn’t directly work in a non-Tailwind project.

- **Tailwind with CSS Variables:** Even without DaisyUI, one can use CSS variables in Tailwind. Tailwind allows using `var(--my-color)` in your utility definitions. For example, you might configure Tailwind’s colors to use CSS vars, or use utilities like `bg-[var(--my-bg)]`. The Evil Martians team wrote about using CSS variables with Tailwind to enable runtime theming, combined with the new OKLCH color format for better contrast handling. They note that simply swapping a color variable at runtime is easy – “just change a CSS variable, and bam, you’re golden” in theory – but ensuring the result looks good in all contexts is tricky ([Better dynamic themes in Tailwind with OKLCH color magic—Martian Chronicles, Evil Martians’ team blog](https://evilmartians.com/chronicles/better-dynamic-themes-in-tailwind-with-oklch-color-magic#:~:text=match%20at%20L151%20variable%2C%20and,isn%E2%80%99t%20everyone%20on%20that%20bandwagon)). Their solution uses the OKLCH color space to generate complementary tones on the fly so that user-chosen colors still meet contrast requirements ([Better dynamic themes in Tailwind with OKLCH color magic—Martian Chronicles, Evil Martians’ team blog](https://evilmartians.com/chronicles/better-dynamic-themes-in-tailwind-with-oklch-color-magic#:~:text=angle%2C%20and%20the%20second%20column,After%20changes%20in%20HSL%2C%20the)) ([Better dynamic themes in Tailwind with OKLCH color magic—Martian Chronicles, Evil Martians’ team blog](https://evilmartians.com/chronicles/better-dynamic-themes-in-tailwind-with-oklch-color-magic#:~:text=let%20users%20pick%20one%20or,still%20generate%20them%20at%20runtime)). This highlights a limitation of simple theming: if users can pick arbitrary colors, you may need logic to adjust text colors or related hues to maintain accessibility.

- **Utility Generator Plugins:** There are also Tailwind-compatible plugins and config tricks for theming. For instance, using `darkMode: "class"` in Tailwind lets you switch to a dark palette by toggling a class on `<html>`. Similarly, one could define custom theme classes (e.g., `.theme-blue { --primary: ...; --secondary: ...; }`) and then have `<body class="theme-blue">`. Some community plugins generate such classes from a config of themes (analogous to DaisyUI’s approach). The key point is that Tailwind’s static nature means you plan the themes ahead of time. On the plus side, this approach can be very performant (all styles precomputed) and easily integratable (just add/remove classes).

## Theming in React (CSS-in-JS vs CSS Variables)

In React and other component-based frameworks, theming is often handled by libraries or context providers:

- **CSS-in-JS Theming:** Libraries like Styled-Components, Emotion, Chakra UI, and Material-UI (MUI) use a Theme Provider pattern. The theme is a JavaScript object (with colors, spacing, etc.) provided via React Context to styled components. Switching themes typically means providing a different theme object (for example, toggling between a light and dark object). This is effective for predefined modes and is integrated with the component library (e.g., MUI’s `ThemeProvider` or Chakra’s `useColorMode` hook). However, as noted by experts, using React context for theming can be overkill if you just need to swap some colors ([Use CSS Variables instead of React Context | Epic React by Kent C. Dodds](https://www.epicreact.dev/css-variables#:~:text=Let%27s%20look%20at%20a%20simple,really%20don%27t%20need%20to%20do)). It can trigger re-renders of many components and tightly couples styling to React.

- **Runtime JS Theme Updates:** Some libraries allow dynamic updates. For example, Chakra UI doesn’t have an out-of-the-box color picker, but you could merge a new color into its theme object and update the context. MUI v5 introduced an **experimental CSS Variables API** where design tokens are also available as CSS custom properties, enabling dynamic theme changes without recalculating styles in JS (MUI’s documentation notes it uses CSS vars under the hood for its new style engine ([Where is the dynamic style? - Ant Design](https://ant-design.antgroup.com/docs/blog/hydrate-cssinjs#:~:text=Where%20is%20the%20dynamic%20style%3F,generate%20styles%20at%20runtime%2C))). In such systems, integration with React is native (since they *are* React libraries), but using them outside React would not apply (they target React components specifically).

- **Direct CSS Variable Use in React:** Another approach (recommended by some devs) is to bypass context and use global CSS variables even in React apps. For instance, you can include a global CSS file that defines `:root { --primary: ... }` and use normal CSS (or CSS-in-JS with `var(--primary)` in styles). Then use a simple JS function (perhaps via a custom hook) to update those variables on user interaction. This way, the heavy lifting is done by the browser’s CSS engine. The **benefit** is that any part of the app (including plain HTML or third-party components) that uses the CSS variable will update, and you avoid large re-renders. The **downside** is that your styling needs to be planned to use those variables; if you have many dynamic theme attributes, managing them can become manual. Still, this method is highly flexible and framework-agnostic. It also aligns with what we discussed above in framework-agnostic solutions, just applied in a React context.

- **Integration & Limitations:** React-specific theming solutions integrate tightly with React (easy to use within React apps, but not outside). They often do not automatically handle things like *system color scheme* or *persisting user choices* – the developer must implement that logic (e.g., reading `prefers-color-scheme` or using `localStorage`). Additionally, many are limited to switching among predefined themes (light/dark or a few options). If an app needs to let users pick arbitrary brand colors, a custom solution (likely involving CSS vars and state) is needed. This is where a new library could improve the developer experience by bridging the gap (providing an API to easily set individual token values and maybe generate the rest of the palette).

## Theming in Angular and Vue

**Angular:** Angular Material’s default theming uses compile-time Sass variables, but there are community solutions for runtime theming. A notable example is **angular-material-css-vars**, which modifies Angular Material to use CSS variables instead of fixed values. This library allows changing the Material palette at runtime by exposing an Angular service to set colors ([angular-material-css-vars - npm](https://www.npmjs.com/package/angular-material-css-vars#:~:text=)). It even includes an *auto-contrast* feature to ensure text is legible: if enabled, it will automatically choose a high-contrast text color (black/white) based on the background hue ([angular-material-css-vars - npm](https://www.npmjs.com/package/angular-material-css-vars#:~:text=,%60setDarkTheme%28isDark%3A%20boolean)). This is important for accessibility – developers can trust that if a user picks a very light or dark primary color, the library will adjust text to remain readable. Integration is specific to Angular (you import an NgModule or provider), but then it works similar to the CSS var approach (calls to change theme ultimately update CSS vars globally).

- **Brand Control:** In Angular Material’s theming approach (and this library), the app developers define which palette slots exist (primary, accent, warn, etc.). A brand could limit user customization to, say, only the accent color by simply not exposing controls for primary. However, out of the box, these libraries won’t enforce “allowed” ranges or palettes – that’s left to the implementer’s UI.

- **Limitations:** The example library currently only supports Material Design v2 (not the newer M3 design) ([angular-material-css-vars - npm](https://www.npmjs.com/package/angular-material-css-vars#:~:text=,be%20found%20in%20this%20issue)), which is a real-case limitation – keeping up with upstream framework changes is a challenge. Also, it’s fairly tied to Angular Material components (not a generic CSS var theming for any CSS in the app). If the app has non-Material styles, you’d need to integrate those into the CSS variable scheme too.

**Vue:** Vue applications often use UI frameworks like Vuetify or Element Plus, which have their own theming systems. **Vuetify 2** allowed enabling CSS custom properties for theme colors (`customProperties: true` in its config) so you could dynamically change them, and **Vuetify 3** goes further with a built-in ability to manage themes at runtime. In Vuetify 3, you can define multiple themes (light, dark, etc.) in the Vue app’s createVuetify configuration and then toggle the active theme via its `useTheme()` hook or the global theme object. Vuetify automatically maps your theme definition into CSS variables. When you switch the active theme, *“Vuetify automatically updates all CSS variables and component styles, ensuring seamless visual transitions without manual DOM manipulation”* ([Theme customization - Build Professional UI with Vuetify Components and Design | StudyRaid](https://app.studyraid.com/en/read/12385/399962/theme-customization#:~:text=This%20implementation%20provides%20persistent%20theme,transitions%20without%20manual%20DOM%20manipulation)). This integration is very smooth in Vue: all Vuetify components respond to the theme change instantly, and you can even watch for OS-level dark mode by default.

- **Element Plus:** Another Vue library, Element Plus, uses a similar approach. They provide an *“element-plus-dynamic-theme”* package ([element-plus-dynamic-theme CDN by jsDelivr](https://www.jsdelivr.com/package/npm/element-plus-dynamic-theme#:~:text=element,save%20element)) which is based on CSS variables. It allows switching theme colors on the fly. Typically, you configure the primary color and it generates variants.

- **PrimeVue/PrimeNG:** PrimeFaces libraries (PrimeNG for Angular, PrimeVue for Vue) use a design token system with CSS variables as placeholders ([Theming - PrimeNG](https://primeng.org/theming#:~:text=PrimeNG%20is%20a%20design%20agnostic,in%20options)). PrimeNG defines a *base* theme (CSS structure with var() references) and *presets* which are basically JSON design tokens mapping to those variables ([Theming - PrimeNG](https://primeng.org/theming#:~:text=the%20components%20using%20the%20themes,be%20configured%20with%20different%20presets)). This design is quite flexible: you can have multiple presets (e.g., “coffee” theme, “solarized” theme, etc.) and swap which preset’s values are applied by swapping the CSS variables (either via a class or by loading another CSS file). To toggle dark mode, PrimeNG suggests either using the `prefers-color-scheme: dark` media query or a manual `.dark-theme` class to switch the variables ([Theming - PrimeNG](https://primeng.org/theming#:~:text=match%20at%20L287%20The%20CSS,See%20the%20dark%20mode)). So integration is often manual toggling of a class. The theming itself is framework-agnostic (just CSS vars), but PrimeNG’s components are built to read those specific vars.

- **Limitations:** In PrimeNG/PrimeVue’s approach, while you *could* change individual variables at runtime (since they’re just CSS vars), there isn’t an off-the-shelf UI control to do so – you’d have to build one. Also, because the theme tokens are hierarchical (primitive -> semantic -> component), simply changing one color might not be enough; you might want to swap a whole preset to ensure a harmonious set of colors. Brands using PrimeNG usually develop a custom preset (their brand palette) and then perhaps allow users to toggle between a couple of presets (e.g., default vs high-contrast). It’s not common to give end-users a color picker for each token.

## Accessibility Presets and Features

Most theming tools prioritize **light/dark mode** support, but **accessibility** features like color-blind friendly modes or high-contrast modes are less common out of the box. Here’s what we found:

- **High Contrast Mode:** Some systems acknowledge it. For instance, modern CSS has a media query for user’s preferred contrast (`prefers-contrast`). A LogRocket article demonstrates using this to offer a “high contrast” toggle for users, allowing a switch to a specially designed high-contrast theme ([Creating contrast themes with CSS prefers-contrast and JavaScript - LogRocket Blog](https://blog.logrocket.com/creating-contrast-themes-css-prefers-contrast-javascript/#:~:text=The%20%60prefers,more%20browser%20support%20than%20others)) ([Creating contrast themes with CSS prefers-contrast and JavaScript - LogRocket Blog](https://blog.logrocket.com/creating-contrast-themes-css-prefers-contrast-javascript/#:~:text=although%20some%20have%20more%20browser,support%20than%20others)). This would typically involve a separate set of CSS variables or classes for the high-contrast theme (e.g., using pure black and yellow, or other WCAG AA/AAA compliant colors). So while not a “library” per se, the technique can be implemented in any theming solution by defining an extra theme variant. Some design systems (like Fluent UI for Windows) provide high-contrast themes that activate when OS high-contrast is on.

- **Color Blind Palettes:** It’s rare to see a built-in “color blindness” mode in libraries. Usually, the guidance is to design your palette to be color-blind safe from the start (avoiding problematic color combos). However, Adobe’s open-source tool **Leonardo** directly addresses this. Leonardo is a tool and npm library for generating adaptive color themes with accessibility in mind. With Leonardo’s JS library, *“users can change the overall contrast, brightness, and saturation”* of a theme dynamically ([Leonardo](https://leonardocolor.io/#:~:text=End)). It can also *“automatically cycle through your colors to create a colorblind safe palette”* by ensuring sufficient differentiation and contrast ([Leonardo](https://leonardocolor.io/#:~:text=Colorblind%20safe%20colors%20made%20easy)). This is a more advanced approach that could be integrated into a theming system – e.g., your new package could use Leonardo’s algorithms to adjust a user-chosen color scheme for various vision deficiencies, or offer one-click presets like “Protanopia-safe colors”.

- **Auto Contrast Text/Icons:** As mentioned, the Angular Material CSS vars solution includes auto contrast for text ([angular-material-css-vars - npm](https://www.npmjs.com/package/angular-material-css-vars#:~:text=,%60setDarkTheme%28isDark%3A%20boolean)). Many custom theming implementations also add logic like: if the user picks a background color, automatically set text to black or white depending on luminance. This can be done in CSS (some use `color-contrast()` in CSS Color Level 5 spec, which is experimental), or in JS by calculating relative luminance. It’s an important feature to prevent users from accidentally creating illegible themes. Not all libraries handle this; those that do (like the Angular one) improve accessibility of user-generated themes.

- **Presets for Disabilities:** The FINOS Accessibility Theme Builder project suggests generating themes that cater to different disabilities (dyslexia-friendly fonts, seizure-safe motion, etc.), but that’s beyond just color. Focusing on color: a new theming tool could include preset themes like *“Colorblind Safe”* (which might replace a troublesome color like red/green with blue/orange alternatives) or *“High Contrast”* (maximizing contrast ratios). Today, developers must craft these manually if desired – an opportunity for a new solution to stand out.

- **Contrast Checking Tools:** While not part of the theming libraries themselves, developers sometimes use tools to test that any user-selectable color combinations maintain contrast standards. A robust theming system could incorporate warnings or adjustments (e.g., if a user picks a very low-contrast combination, the system could alert them or auto-adjust slightly).

In summary, accessibility-related theming support is still mostly manual or provided by guidelines rather than integrated into mainstream theme switchers. This is a gap a new library could fill (for example, by building on something like Adobe Leonardo’s approach to ensure any theme is accessible by design).

## Brand Control and Customization Constraints

When offering theme customization (especially in product platforms where end-users or clients can rebrand an app), brands often want to maintain some control so that the result still aligns with their identity and design guidelines:

- **Limiting Adjustable Variables:** Many existing solutions allow full freedom within the defined theme properties – if you can change the primary color, you can technically set it to any hex code. If a brand needs to restrict choices (say only allow picking from their official color palette, or not altering certain key colors like the company logo color), this typically isn’t enforced by the theming library itself. Instead, the application’s UI must impose those rules (e.g., offering a dropdown of approved colors rather than a free-form color picker). We didn’t find an out-of-the-box library that supports locking certain variables or value ranges as a feature. It’s an area for improvement.

- **Preset Themes vs. Freeform:** Some organizations choose to offer **preset themes** rather than freeform customization. For example, a SaaS product might have a “default”, “brand A”, “brand B” theme hard-coded, to ensure each is visually coherent. Tools like DaisyUI or PrimeNG are geared towards such preset usage. In contrast, truly freeform theming (where a user can tweak multiple colors arbitrarily) is less covered by existing libraries. If implementing freeform, one must consider the aforementioned contrast issues and unpredictable combinations. The Evil Martians article pointed out that letting users pick arbitrary colors means you cannot predefine complementary colors, but they can be **generated at runtime** with smart algorithms ([Better dynamic themes in Tailwind with OKLCH color magic—Martian Chronicles, Evil Martians’ team blog](https://evilmartians.com/chronicles/better-dynamic-themes-in-tailwind-with-oklch-color-magic#:~:text=match%20at%20L211%20let%20users,still%20generate%20them%20at%20runtime)) ([Better dynamic themes in Tailwind with OKLCH color magic—Martian Chronicles, Evil Martians’ team blog](https://evilmartians.com/chronicles/better-dynamic-themes-in-tailwind-with-oklch-color-magic#:~:text=let%20users%20pick%20one%20or,still%20generate%20them%20at%20runtime)). A new library could incorporate such algorithms, allowing some freedom while auto-adjusting secondary colors to keep the theme harmonious.

- **Real-World Example – WordPress Customizers / Shopify:** Outside of pure JS libraries, consider WordPress theme customizers or Shopify theme editors. These allow admins to change colors via a UI, but typically the theme developer decides which “accent” or “background” colors are user-configurable. The underlying mechanism often ends up updating CSS variables or generating a custom CSS file. The key is that the *scope* of customization is controlled. A comparable approach in an npm package could be to let developers define a schema of customizable tokens (e.g., mark primary and secondary as user-configurable, but fix all others). The tool could then present a generic UI or API to only change those.

- **Brand Consistency Checks:** We didn’t find explicit “brand consistency” enforcement in libraries, but a brand might, for instance, allow only lighter/darker variations of their core color. One could envision a theming tool feature: e.g., define a base brand color and only allow the user to adjust its brightness/saturation within a range, rather than choosing an entirely unrelated hue. Today, implementing that logic is up to the developer building the customization interface.

## Notable Limitations in Existing Solutions

Across the existing solutions we researched, some common limitations and missing features emerged:

- **Framework Specificity:** Many solutions are tied to a specific stack. For example, Angular Material’s CSS var theming is wonderful for Angular + Material, but useless elsewhere. A React Context theme provider is great in React, but not for a static HTML page. Even DaisyUI, while just CSS, assumes Tailwind usage. This fragmentation means there’s no one-size theme library you can use across React, Vue, and Angular easily. **Opportunity:** a new package could aim to be framework-agnostic at core (pure CSS/JS) but provide thin adapters for React (e.g. a hook), Angular (service), etc., to integrate smoothly.

- **Lack of Advanced UI Controls:** Existing theme switchers mostly handle “switching themes” (choosing from a set). If you need a UI for users to pick custom colors, you’re building it yourself. There’s no popular npm package that provides a ready-made color customization widget that plugs into your app and theme system. A few design systems have internal tools (e.g., Salesforce’s theme builder for their platform, or FINOS Theme Builder for generating tokens) but these aren’t drop-in for general apps. A new library that includes a UI component for selecting and previewing theme changes could be valuable.

- **Limited Number of Variables:** Simpler libraries often only handle a handful of variables (like primary/secondary). If your theme is more extensive (dozens of color tokens plus maybe spacing or border radius), you need a more robust solution (or multiple libraries). Some CSS-in-JS solutions can handle many properties but at cost of complexity. PrimeNG’s design token system can scale to many tokens, but it’s complex to configure. There’s a trade-off between simplicity and flexibility.

- **Dynamic Generation of Palettes:** When a user selects a single base color, how do the other shades get determined? Many tools *don’t handle this at all* – they expect a full theme object. That leaves the problem to the developer or designer to solve (for instance, picking a primary color and manually choosing lighter/darker versions for hover states, etc.). Tools like Adobe Leonardo fill this gap by generating a consistent palette given some inputs (ensuring contrast ratios, etc.). Most mainstream frameworks don’t integrate such functionality yet (the Evil Martians’ Tailwind approach with OKLCH is a bleeding-edge example for custom logic). This is a feature area a new library could improve: generate missing theme values automatically (with safe defaults) so that a user who picks one or two colors can still get a complete, accessible theme.

- **Performance and FOUC:** Nearly all CSS variable solutions are very fast once loaded (changing a var is instantaneous). But one limitation is initial load flash, as mentioned. Storing theme in localStorage is common, but applying it requires JS to run. Some libraries (like theme-change) mitigate this by inlining a script early. Another approach is server-side rendering the user’s theme (if known), but that’s outside the scope of these tools. It’s worth noting that CSS media queries (like `prefers-color-scheme`) can automatically apply dark mode without JS, but for custom themes, there’s no native equivalent. A best practice is to add a `[data-theme]` attribute on the `<html>` with a default (or user’s last choice) as early as possible.

- **Stateful Complexity in Apps:** In React or similar, if you rely solely on CSS variables, you need to ensure components that need to know the theme (for logic) subscribe to changes. Conversely, if you use context, you risk performance overhead. Neither approach is perfect alone. Some newer libraries (e.g., MUI’s CssVarsProvider) try to combine the benefits by syncing a CSS var theme with React state. Still, this area can be tricky, especially if multiple theme customizations (color, density, font size) are happening together.

- **Missing Multi-Framework Support:** If you maintain design consistency across multiple platforms (say a web app and a native mobile app), design tokens are often used (like a JSON of colors). Many web theming solutions don’t directly tie into design token workflows or cross-platform needs. A forward-looking theming package might allow import/export of token sets, or integration with design tools (maybe reading a style dictionary or JSON). We didn’t delve deeply here, but it’s a consideration for a “better” solution.

## Key Takeaways and Recommendations

**Key Takeaways from Existing Solutions:**

- *CSS Variables are the de facto standard* for runtime theming on the web. They enable instant theme changes without repainting everything, and are supported in all modern browsers ([How to create better themes with CSS variables - LogRocket Blog](https://blog.logrocket.com/create-better-themes-with-css-variables/#:~:text=preprocessors%20like%20Sass%20and%20Less,Let%E2%80%99s%20get%20started)) ([How to create better themes with CSS variables - LogRocket Blog](https://blog.logrocket.com/create-better-themes-with-css-variables/#:~:text=CSS%20variables%20create%20a%20smoother,of%20styles%20for%20our%20components)). Most new theming libraries leverage them (either directly or under the hood in CSS-in-JS). Any new solution should do the same for performance and compatibility.

- *Framework-specific approaches (Tailwind, Material-UI, Vuetify, etc.) implement dynamic theming in their own ways*, but the concepts overlap. Usually, define themes (or tokens) in a config, then apply via a class, context, or service. Integration is smooth within those ecosystems but hard outside. A successful new library might act as a bridge or alternative: e.g., it could work with plain CSS but also play nicely with Tailwind (by generating a Tailwind config or using utility classes) **and** with React (by offering hooks to sync theme state).

- *Accessibility considerations are often left to developers.* Out-of-box support for high contrast or color-blind friendly themes is minimal in most tools. However, technologies exist to address this (like Adobe’s Leonardo for generating accessible color palettes ([Leonardo](https://leonardocolor.io/#:~:text=Leonardo%E2%80%99s%20npm%20module%20can%20be,and%20saturation%20of%20their%20experience)) ([Leonardo](https://leonardocolor.io/#:~:text=Colorblind%20safe%20colors%20made%20easy))). There’s room for a theming library that bakes in accessibility: for example, always computing a complementary text color with sufficient contrast, offering an optional “increase contrast” toggle, or ensuring a minimum contrast ratio for any user-chosen color (perhaps by nudging the value).

- *Brand control is usually achieved through preset limitations rather than dynamic enforcement.* Current solutions allow either fixed theme choices (brand-approved) or complete freedom. A gap exists for “constrained customization,” where a brand can say “users can pick from these 5 accent colors” or “the base background must remain light”. Implementing this would likely involve the library providing a configuration to lock or restrict certain variables or values.

- *Most dynamic theming libraries focus on colors.* Other style aspects like spacing or typography scales are less commonly user-adjustable at runtime (except maybe toggling a “large text mode”). If the new package is primarily about color theme, that’s fine – just note that existing solutions haven’t pushed much into other style properties dynamically, except for dark mode adjustments.

**Recommendations for a New NPM Package:**

1. **Make it Framework-Agnostic, with Adapters:** The core should manipulate CSS variables (and possibly provide CSS for defaults) so it can work anywhere. Then provide small adapters or examples for popular frameworks:
   - A React hook or context that syncs the theme (for devs who prefer that pattern).
   - An Angular service that wraps the DOM updates.
   - Utilities for Vue (though simply using `provide/inject` or reactive vars to call the updater might suffice).
   - Integration with Tailwind could be via documentation on how to use Tailwind’s `apply` or config to reference the CSS vars that the library manages.

   *Rationale:* This broad compatibility will set it apart from solutions locked into one stack.

2. **Design a Token System with Controlled Customization:** Allow defining a set of design tokens (colors, maybe others) and mark which are user-adjustable. For example, a library config could list tokens like primary, secondary, background, etc., each with default values and flags like `editable: true/false`. The package can then generate the CSS variables and provide functions to update only the editable ones. This way, brands/developers retain control. You could even allow constraints (like value ranges or preset options for a token). Essentially, treat it as a **theming schema**.

3. **Include Accessibility Utilities:** Differentiate by doing what others don’t:
   - Automatic contrast checking: whenever a color is set, ensure the paired foreground/background has enough contrast. Possibly expose a setting like `enforceContrast: AA` to always meet WCAG AA. Use CSS `color-contrast()` or JS calculations to adjust as needed.
   - Optional color-blind mode generation: Provide a function to transform a theme into a color-blind-safe variant (perhaps using known safe color swaps or algorithms). For instance, if a user enables “color-blind friendly” mode, the library could shift hues that clash (red/green) into alternatives. Even simply offering a monochrome high-contrast mode as a fallback could be helpful.
   - Respect system settings: Offer an easy way to hook into `prefers-color-scheme` or `prefers-contrast`. E.g., allow the config to have a “dark” sub-theme and automatically apply it if system dark mode is on (unless user overrides). This makes the library feel modern and considerate.

4. **Palette Generation and Linking:** If a user is only allowed to pick a limited set of colors (say a primary), the library should generate related colors (like hover shades, or complementary colors) automatically. This could be done via HSL or OKLCH manipulation as suggested by Evil Martians, ensuring that adjusting one value doesn’t break the whole theme’s look ([Better dynamic themes in Tailwind with OKLCH color magic—Martian Chronicles, Evil Martians’ team blog](https://evilmartians.com/chronicles/better-dynamic-themes-in-tailwind-with-oklch-color-magic#:~:text=let%20users%20pick%20one%20or,still%20generate%20them%20at%20runtime)). Providing sane defaults (maybe a slight lighten/darken for hover states, etc.) will save developers time and result in more consistent theming. For advanced use, integrate with or incorporate something like Leonardo’s contrast-based generation for truly adaptive palettes.

5. **Multiple Theme Support & Storage:** Allow defining multiple named themes (like CSS classes or data-attributes) *and* support per-user custom themes. The library could manage a list of themes – e.g., built-ins like Light, Dark, HighContrast, and any number of user-saved themes. Provide functions to switch themes by name and to save/load a theme (perhaps with localStorage integration out of the box). Essentially, combine the idea of “preset themes” and “custom theme” in one system. This would cover both use cases: simple toggles and advanced customization.

6. **Integration with Tailwind (optional but useful):** For Tailwind users, consider an option to output Tailwind config or classes for the theme. For example, the package could generate a Tailwind plugin that creates utility classes based on the tokens (similar to how PrimeNG maps tokens to CSS classes). This way, Tailwind projects can still use utilities referencing the dynamic theme (though they’d still rely on CSS vars at runtime). At minimum, show how to use Tailwind’s `var(--color)` approach so that Tailwind components respond to theme variable changes.

7. **Document Limitations & Provide Escape Hatches:** A good new library should be clear about what it doesn’t do (at least in v1). For instance, if it focuses on colors, note that and perhaps suggest how users might integrate font size toggling if needed. Ensure there’s a way for developers to extend it – e.g., allow adding their own CSS variables to the theme system in case they have a very app-specific variable to include.

By learning from existing solutions, a new package can improve on them by being more flexible and accessibility-aware. The combination of **CSS variable power**, **cross-framework compatibility**, and **built-in accessibility/branding controls** would make it a strong tool for dynamic theming needs.
